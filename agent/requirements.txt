# "pip install -r". Was hier steht, landet in Lib/site-packages der

#
# WER SIE NICHT LIEST: das .deb. Dort kommen die Bibliotheken aus den

# python3-cryptography" in build_deb.py) und haengen an der Systempflege,
# nicht an dieser Datei. Auch setup.sh und der Watcher fassen sie nicht

#
# Bis 0.37.2 las sie NIEMAND: build_msi.py zaehlte die Paketnamen selbst
# auf, ohne Versionen. Damit war jeder Bau ein anderer, es gab kein
# Verzeichnis des Ausgelieferten, und ein Pin hier war eine Notiz, die
# wie eine Absicherung aussah. Gefunden bei der Sicherheitspruefung am
# 2026-08-29 (F-14), nachdem tags zuvor an genau dieser Datei ein Befund
# "behoben" worden war, der das ausgelieferte Paket nie erreicht hat.
#
# ALLES gepinnt, auch was nur mittelbar hereinkommt: cffi und pycparser
# haengen an cryptography, certifi/charset-normalizer/idna an requests.
# Bliebe eines davon offen, waere die Luecke wieder da, nur kleiner.
# build_msi.py bricht ab, wenn nach dem Installieren etwas in
# site-packages liegt, das hier nicht steht, oder in einer anderen
# Fassung. Ein neuer mittelbarer Abhaengiger faellt damit beim Bauen auf
# und nicht beim Kunden.
#
# Beim Anheben: pip-audit ueber diese Datei laufen lassen und den
# Windows-Agent danach einmal wirklich installieren. Stand geprueft am
# 2026-08-29 - pip-audit meldet null Befunde.
#
# Beim Wechsel der Python-Nebenversion (PY_VERSION in build_msi.py) den
# pip-Aufruf mit der neuen Zahl trocken laufen lassen: die Raeder muessen
# fuer die Ziel-ABI vorliegen. Am 2026-08-31 fuer 3.14 geprueft - dieselben
# acht Fassungen wie unter 3.12, cffi und charset-normalizer mit echten
# cp314-Raedern, cryptography ueber abi3 (cp311-abi3 gilt auch fuer 3.14).
# Die Datei musste dafuer nicht geaendert werden.
#
# HASHES (die letzte Haertung aus der Pruefungsliste, 2026-09-04)
#
# Ein Pin sagt "diese Fassung". Er sagt nicht "diese Datei". Wer ein
# PyPI-Konto uebernimmt, kann eine Veroeffentlichung zurueckziehen und
# unter derselben Nummer eine andere Datei hochladen - der Pin passt
# weiterhin, und das MSI wuerde den neuen Inhalt einsammeln, mit dem
# Release-Schluessel signieren und als SYSTEM auf jeden Windows-Host
# ausliefern. Genau die Kette, die F-07 fuer den eigenen Code schliesst,
# lag fuer die Bibliotheken daneben offen. Stand seit der dritten
# Pruefungsrunde als "Restrisiko, bewusst offen" (F-14).
#
# --require-hashes im pip-Aufruf macht daraus "diese Datei". Es zieht
# ausserdem zwei Regeln nach, die pip dann selbst erzwingt: jede
# Anforderung muss mit == gepinnt sein, und es darf keine ungenannte
# mittelbare Abhaengigkeit hereinkommen.
#
# WAS HIER STEHT, sind genau die acht Dateien, die der Bau auswaehlt -
# nicht alle Dateien der jeweiligen Fassung. charset-normalizer allein
# haette 172. Die Auswahl haengt an drei Dingen im pip-Aufruf von
# build_msi.py: --platform win_amd64, --python-version aus PY_VERSION und
# --only-binary=:all:.
#
# DESHALB: wer PY_VERSION anhebt, muss die Hashes NEU ERZEUGEN. Die
# ABI-gebundenen Raeder (cffi, charset-normalizer) heissen dann cp315
# statt cp314 und sind hier nicht aufgefuehrt - der Bau bricht mit einem
# Hash-Fehler ab. Das ist gewollt: er soll anhalten und nicht raten.
#
#     python3 tools/pin-hashes.py            # zeigt, was sich aendert
#     python3 tools/pin-hashes.py --schreiben # traegt es ein
#
